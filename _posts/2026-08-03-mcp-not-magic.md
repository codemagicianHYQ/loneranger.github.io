最近推特上 MCP 出现的频率有点夸张，好像接了就能「Agent 起飞」。

我实际接过几次：文档站、本地文件、GitHub 相关能力。结论先说：

**有用，但没那么神。**

## 它到底是什么

按我的理解，MCP（Model Context Protocol）更像是：

> 给大模型外面挂一层「标准插头」，让它能调外部工具。

以前每个工具自己写一套 function calling。  
MCP 想做成通用协议——IDE、CLI、自己写的小服务，都能按同一套方式接进去。

所以它解决的是 **接线方式**，不是智商。

模型还是原来的模型。接了烂数据源，照样胡说八道。

## 我什么时候觉得它香

比较明显的是这几类：

1. **反复要查外部状态**  
   比如仓库 issue、某份在线文档、数据库里的表结构。每次复制粘贴太烦。

2. **工具要在多个客户端复用**  
   Cursor 用一套，Claude Code 也想用同一套能力。MCP 至少省掉重复封装。

3. **权限边界比较清楚**  
   某个 server 只读 GitHub，不给写权限。比「把所有钥匙都塞进 prompt」安心一点。

## 什么时候我觉得没必要

- 任务就是改本地几个文件：直接让 Agent 读仓库就行，硬上 MCP 纯属加戏。
- 自己写个一次性脚本更快：为了「用上 MCP」而接，属于工具强迫症。
- server 不稳定：超时、鉴权失败、返回一坨半截 JSON，Agent 会顺着错误继续演。

有一次我接了个文档 MCP，结果返回的是旧版接口说明。  
Agent 写得很自信，我联调半天才发现文档源就错了。  
那次之后我养成习惯：**外部工具给的东西，默认先怀疑。**

## 和 function calling 怎么区分

有人问「那不就是 tools 吗」。

差不多，但层次不同：

- function calling：这次对话里模型能调哪些函数
- MCP：这些函数/资源怎么被不同宿主发现、连接、鉴权

你可以没有 MCP，照样做 Agent。  
MCP 更多是工程上的标准化，像 USB，不是新芯片。

## 现在怎么用

我给自己定的规矩很土：

- 先问：没有它，我会不会每周重复粘贴同一种上下文？会 → 再考虑接
- 每个 MCP 权限尽量最小
- 出问题先看工具返回，再看模型总结

别被 demo 骗了。  
demo 里永远是「一键连接全世界」；真实项目里永远是 token 过期、权限不够、返回格式变了。

Claude Code / Cursor 这圈子里，Skill、Agent、Subagent、Rules 名词太多。

我一开始也混。后来干脆不管官方定义，按自己的使用场景硬分：

## 我的分法

**Skill**：固定流程说明书。  
「怎么提交」「怎么写 blog front matter」「怎么查 Jeecg 签名问题」——步骤稳定，可以写成文档让工具每次照着做。

**Agent**：这次任务的执行者。  
给它一个目标，它现场决定读哪些文件、跑什么命令。

**Rules**：全局脾气和禁区。  
比如「别动 .env」「中文回复」「不要擅自 force push」。

一句话：

> Skill 管「怎么做这类事」，Agent 管「这次具体去做」。

## 为什么 Skill 突然变香

以前我每次都口述：

> 先看 git status，再看 diff，提交信息要写清楚 why，不要把 .env 加进去……

说三遍就烦了。写成 Skill 之后，同类任务直接引用，漏步骤的概率下降。

尤其是提交规范、发版检查、博客文章模板这种——**你自己都标准化了的东西**，最适合进 Skill。

## 翻过的车

### 1. Skill 写太长

我写过一个「万能前端排查」Skill，又长又全。  
结果模型每次都想把整份说明书跑一遍，明明只是改个样式。

后来改成短 Skill：一个 Skill 只干一类事。提交归提交，联调归联调。

### 2. 把判断题也写死

Skill 里写「一律用某某方案」。  
遇到例外场景它就硬套。  
现在我会在 Skill 里留一句：边界情况先问人。

### 3. 和 Rules 职责打架

Rules 说「谨慎改配置」，Skill 又教「直接改 \_config.yml」。  
两边冲突时，Agent 行为会飘。  
我现在尽量：Rules 管红线，Skill 管流程。

## 什么不值得做成 Skill

- 只做一次的实验
- 还在剧烈变化的流程
- 需要大量业务上下文、写不全的东西

Skill 不是知识库百科。  
它更像你们组那份「上线 checklist」——短、可执行、常复用。

## 一点体感

写 Skill 的过程，其实是在逼自己把隐性经验显性化。

「我平时到底怎么提交的？」  
写着写着才发现：自己也没那么规范。

这可能比 Skill 文件本身更有价值。

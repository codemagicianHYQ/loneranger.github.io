八月刷到不少工程向帖子在讲一件事：别一上来就让 Agent 改代码，先让它出计划。

我以前不爱这样。觉得麻烦，而且「计划」两个字听着像形式主义。

后来连续翻车两次——一次把不该动的配置改了，一次在错误目录里装依赖——开始老实了。

## 我现在的默认流程

中等以上任务：

1. 用一句话说清目标（成功标准）
2. 让 Agent 先列计划：要读哪些文件、改哪些、不动哪些、怎么验证
3. 我改计划（通常是删掉一半「顺便优化」）
4. 再允许它动手
5. 看 diff，跑一下相关命令

小改动（改文案、改一行样式）就跳过，直接干。

## 计划为什么有用

不是因为计划本身神圣。

是因为：

**你被迫在动手前暴露分歧。**

Agent 计划里写「重构整个 request 封装」，你当场就能喊停。  
如果它直接开改，你往往在一堆 diff 里才发现它跑偏了。

另外计划会逼它声明验证方式。  
没有验证步骤的计划，我一般不批。

## 计划写砸的样子

我也见过没用的计划：

```text
1. 分析需求
2. 实现功能
3. 测试
4. 完成
```

这叫正确的废话。

我要的是这种粒度：

```text
1. 读 admin/config.yml 和现有 posts front matter
2. 只新增封面图字段，不改 publish_mode
3. 更新 README 对应小节
4. 本地打开 /admin 看字段是否出现（或至少核对 yaml）
```

越具体越好拦偏。

## 和「规格驱动开发」的关系

外面有人叫 Spec-driven、有人叫 Plan mode。  
名字不重要。

本质都是：

> 把「模糊自然语言」先压成「可执行约束」，再让模型碰代码。

对个人项目，你不需要写完整 RFC。  
半页 bullet 就够。

## 我还在纠结的点

有些任务计划成本比直接试错还高。  
比如「这个报错啥意思」——看一眼 stack trace 更快。

所以不是教条。  
我的规则是：

- 会改多个文件 / 可能破坏环境 → 先计划
- 单点问题 → 直接干
- 不确定有多危险 → 先计划，计划可以很短

## 收尾

Agent 越强，越容易让人懒得想清楚。

计划这一步，其实是把思考权抢回来一点。  
不是为了写文档，是为了少收拾残局。
